# Google Play signing strategy

This document defines the signing model for Scan's mixed distribution:

- Google Play is the preferred end-user channel once public.
- A signed APK may also be distributed directly from the official GitHub Release.
- Both channels must remain update-compatible.

## Decision

For Scan v1, the **permanent Scan production key is the app-signing identity**.

When configuring Play App Signing for `com.thiepn.scan`:

1. Do **not** accept an unrelated Google-generated app-signing identity and then assume the locally signed GitHub APK remains update-compatible.
2. Before any open-testing or production rollout, use Play Console's advanced signing setup to provide Google with a copy of the permanent Scan production app-signing key.
3. Verify the app-signing certificate fingerprint shown by Play matches the certificate fingerprint recorded by Scan's production-signing bootstrap.
4. Keep the private production key backed up outside the repository.
5. A separate upload key is recommended after Play App Signing is established, but changing the CI upload-signing flow should be treated as a separate controlled change.

Google documents two supported ways to keep alternate-distribution installs signed consistently:

- provide Google with the app-signing key you want to use everywhere; or
- let Google generate the app-signing key and distribute the Play-generated signed universal APK outside Play.

Scan uses the first model because the project already supports a permanent direct-release signing identity.

## Why this matters

Android only accepts an in-place app update when the package name and signing lineage are compatible.

If Google Play signs `com.thiepn.scan` with a different app-signing key from the direct GitHub APK:

- a Play-installed copy may reject the locally signed direct APK as an update;
- a direct-APK installation may not be directly replaceable by a differently signed Play build;
- switching channels can require uninstall/reinstall, which is dangerous for Scan because its working document library is app-private and local.

The signing choice therefore affects data-preserving update behavior, not just publishing mechanics.

## Before the first Play rollout

Complete all of these **before any open-testing or production release**:

- [ ] permanent Scan production key created or intentionally reused
- [ ] at least two secure offline backups of the permanent keystore exist
- [ ] keystore passwords stored in a password manager
- [ ] public SHA-256 app-signing certificate fingerprint recorded
- [ ] production acceptance workflow passes on exact current `main`
- [ ] Play App Signing configuration opened in Play Console
- [ ] "provide a copy of your app signing key" selected instead of an unrelated default key
- [ ] encrypted key transfer completed using the current Play Console instructions / PEPK tooling
- [ ] Play app-signing SHA-256 fingerprint compared against the locally recorded production certificate
- [ ] fingerprints match
- [ ] no Play testing/public rollout performed before that verification

## Upload key

Play distinguishes:

- **app-signing key** — the identity Android trusts on installed APKs;
- **upload key** — authenticates bundles uploaded to Google Play.

Using a separate upload key is safer because Google can reset an upload key without changing the app-signing identity.

For Scan v1, do not silently switch the automated AAB signing path to a different upload key during the release freeze. First establish the permanent app-signing identity and publish v1 safely. A dedicated upload-key/CI migration can be performed as a separately certified change afterward.

## Alternate model

If the project later chooses Google's generated app-signing identity instead, the direct-download strategy must change:

- stop advertising the locally signed APK as cross-channel update-compatible;
- download the **signed universal APK** generated by Google Play for the matching bundle;
- publish that Play-signed universal APK as the alternate distribution artifact;
- update the website/release automation and re-test update paths.

Do not mix the two models.

## Evidence to retain

Keep these outside the repository where appropriate:

- permanent keystore backup
- production certificate fingerprint record
- Play app-signing certificate fingerprint
- Play upload certificate fingerprint, if/when separate
- screenshots/export of Play App Signing configuration
- physical-device evidence for Play ↔ direct update compatibility

Never commit private keys or passwords.
